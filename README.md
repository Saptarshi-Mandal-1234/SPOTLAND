# SPOTLAND — Travel PWA

India-first travel PWA with nearby spots/venues, routes, weather, events, crowd reports, optional Google accounts, favorites, trips, live sharing, SOS and offline saved places. Photo uploads are deployed and verified; Web Push receiving is configured, while real delivery testing remains pending and nearby SOS broadcasting stays disabled. The sections below retain each milestone's implementation notes; see `STATUS_REPORT.md` for the current release status and remaining launch gates.

## Live website

**Open SPOTLAND: [https://spotland.pages.dev](https://spotland.pages.dev)**

This is the public internet deployment, accessible from a phone or computer. `http://127.0.0.1:5173` is the separate local development address.

- Frontend: Cloudflare Pages, with installable PWA support.
- Backend: a private Cloudflare Worker reached through the website's same-origin `/api` service binding.
- Storage: Cloudflare D1 for application data and private R2 for moderated review photos.
- Deployed services: production Google sign-in, account-scoped favorites/trips/reviews, photo moderation and automatic expiry cleanup.
- Browsing works without login. Street map tiles require a connection; saved place copies and the app shell support offline use.

Deployment is complete, but general safety launch approval remains pending. Nearby SOS broadcasting is disabled. Physical-device safety/push tests, full accessibility review, legal/operator approval and platform logging/quota checks remain open. See [launch checklist](LAUNCH_CHECKLIST.md) and [verification report](reports/release-checks/scheduled-verification.md). R2 has a free allowance with billable overages; the operator must monitor usage.

## M1 — nearby exploration

Open **Explore nearby** on the home screen. Default area is Delhi; submit a city/landmark search or explicitly request location. Drag the map and use **Search this area**; dragging alone never queries Overpass. Categories and distance filter the list and markers. Select either to see place details. State/UT backdrops can be chosen manually and are detected from submitted search results. Illustrations are original CC0 SVGs, each under 1 KB, with metadata in `states.json`.

Public-provider requirements: [Nominatim policy](https://operations.osmfoundation.org/policies/nominatim/), [OSM tiles](https://operations.osmfoundation.org/policies/tiles/), [Overpass guidance](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html). No autocomplete or tile prefetch. Submitted searches are cached for 24 hours with a global 1.5-second D1 gate. Nearby queries use rounded coordinates, a fixed allowed radius, a 30-minute cache, and a global 5-second gate. Busy requests receive 429, with visible retry. Providers are configurable in Worker vars; never put confidential information into search. This public-provider setup is for modest usage, not guaranteed availability.

`npm run dev` applies local D1 migrations first. To deploy on the free D1 plan, run `npx wrangler d1 create travelapp`, replace the all-zero LOCAL PLACEHOLDER database ID in `worker/wrangler.jsonc` with its returned ID, and run `npx wrangler d1 migrations apply travelapp --remote --config worker/wrangler.jsonc`. Set a real identifying `PROVIDER_USER_AGENT` with an app URL/contact before publishing. Follow the existing Pages/Worker deployment steps. No remote database has been created by this milestone.

Ratings are disabled because OSM does not supply dependable ratings. Open-now uses only explicit 24/7 hours; other hours remain visible without guessing. Public tiles are not eligible for offline downloads; select a compliant provider before M7 map caching. Place data may be missing or stale, and some queries may be capped at 300 results. Live location permission and physical-device performance require user/device review.

## M2 — directions

Select a place → **Directions**. Choose the exploration area, explicitly request current location, or submit a start-location search. Select Walk/Drive/Cycle and press **Get directions**. The map fits the route; **View route on map** scrolls to it. Changing mode or start clears the old route. Closing directions cancels requests and removes the line. **Open in Google Maps** is an outbound directions link with start, destination, and selected mode; no Google API is used.

The adapter uses FOSSGIS OSRM's worldwide car/foot/bike endpoints via `OSRM_URL_TEMPLATE` in Worker vars, a shared 1.5-second D1 gate, 10-minute caching, and a 25-second upstream timeout. See [provider usage and privacy](https://routing.openstreetmap.de/about.html). Coordinates are rounded to 3 decimal places before routing and cache storage; this may shift endpoints by about 100 m. Requests are limited to two points in the India bounds and a straight-line separation up to 100 km. No traffic estimates, background navigation, accessibility guarantees, or offline routing. Physical-device location permission remains a user/device check.

## M3 — weather and best time

Explore → select a place → **Weather & best time**. View the next 48 hourly readings in IST (day/night, temperature, rain probability/amount, wind and conditions). Change Indoor/Outdoor to match the actual visit. Three ranked, non-overlapping two-hour windows use documented scoring in `shared/weather-score.ts`. Supported opening schedules are 24/7 and simple weekday/time ranges, including overnight ranges. Complex/holiday schedules stay unverified; confirm venue hours. Windows do not imply safety or guaranteed access.

Forecast cautions are in-app planning thresholds: thunderstorm WMO codes 95/96/99, heavy rain at 7.5 mm/h or codes 65/82, heat at 35°C+. Storm/heavy-rain windows are excluded; outdoor heat >=35°C or wind >=40 km/h and all heat >=40°C are excluded. These are not official meteorological warnings, and there are no push notifications/background alerts in M3.

Worker adapter `OPEN_METEO_URL` defaults to the official forecast endpoint. Coordinates rounded to two decimal places; forecasts cached in D1 for 30 minutes with original fetch time preserved. A shared 18-second miss gate limits upstream calls to at most 4,800/day for this app. No API key, card, subscription or new dependency. [Open-Meteo terms](https://open-meteo.com/en/terms) allow the free API only for non-commercial use (<10,000/day, 5,000/hour, 600/minute); advertising, subscriptions or commercial launch require a provider decision before release. Do not switch to a paid endpoint. Data attribution is CC BY 4.0, linked in the panel and Attributions page. [API docs](https://open-meteo.com/en/docs).

Review fixes: non-string OSM phones no longer break facility responses; corrupt JSON cache entries recover as cache misses; cancelled mount requests avoid upstream calls; delayed map initialization uses the latest center; safety restore/offline messages identify saved results and reset loading correctly. Public deployment still needs Cloudflare login. Phone installation, real location permission/calls, offline behavior, and launch/legal review remain pending.

Nearby category extension: Shopping malls & centres uses OSM shop=mall. Gaming & internet cafes includes amusement arcades, escape games and internet cafes; confirm actual games with the venue. Cafes remain included. Expanded queries use a new cache key so previous cached responses cannot hide the additions. OSM coverage varies.

## Community events and crowd history

Community events accepts public submissions, keeps them pending and publishes only moderator-approved entries. Set `ADMIN_TOKEN` privately in Worker environment configuration to enable moderation; the moderator screen keeps the token in memory. Local development applies D1 migrations automatically.

Local operator access is configured in git-ignored `worker/.dev.vars`. Copy its `ADMIN_TOKEN` value (without quotes) into Events → Moderator access or Venues → Venue moderator access. Events uses that same token for traveller review and photo moderation. Never share it with visitors. `node scripts/setup-moderation.mjs` creates a cryptographically random token if missing and preserves an existing token; restart `npm run dev` after changing secrets. Production still needs its own Worker secret configuration before moderation is available publicly.

Select any nearby spot to see its crowd check. Voluntary Quiet/Moderate/Busy reports build history without a paid provider or background location tracking. `shared/crowd.ts` computes the empirical busy-report percentage for the same weekday and +/- one hour in IST over the previous 90 days. At least 15 matching reports across three dates are required; otherwise it shows “Not enough data yet”. No historical records are fabricated. The estimate concerns a busy visit, not capacity occupancy, and is not calibrated against observed outcomes. Reports can be biased or manipulated; stronger validation is needed before making accuracy claims.

Crowd reports expire after 90 days on API access. Three reports per network per day, a 30-second cooldown and one report per spot/network/day limit abuse; shared networks share limits. A daily SHA-256 network hash is stored for deduplication, not raw IP addresses; this hash is pseudonymous and is not a guarantee of anonymity. Update the privacy policy and obtain the required launch/legal review before public collection. No new dependency, paid API or cloud resource was introduced.

## M4 part 3 — optional external events

No account, key, card or paid API is used. This is community-maintained open data, **not an organiser's official event calendar**. Coverage of future Indian events is sparse. The bounded query includes India-country records classified as festivals, concerts, exhibitions or sports competitions, with day-precision event/start dates. It omits undated recurring festivals, coarse year/month dates and records without an explicit India country statement. Multi-day events are currently displayed by start date only.

Browse **Community events → Load Wikidata events**. Today/weekend/upcoming filters apply to both community and external lists; the map merges available coordinates. Each external card has a source link for verification/correction and a distinct open-data label. Only a record's own coordinates create a pin; no city centroid or invented venue is mapped. Wikidata records never enter the approved community-events database.

Restart local development after changing configuration.

The adapter caches all successful responses, including empty lists, in D1 for six hours. ### Google setup (public client ID, no API key or client secret)

1. Follow the official [Google Identity Services setup](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid). In Google Cloud Console select/create a project and open Google Auth Platform. Configure Branding, Audience (External unless using a Workspace organization) and the consent screen. In testing, add your own Google account as a test user if required. Use only basic Google sign-in; no Maps, Firebase Identity Platform, paid API, billing account or card is needed for this app integration. Do not enable paid services.
2. Create a client of type **Web application**. Under Authorized JavaScript origins add the exact app HTTPS origin, for example `https://YOUR-PROJECT.pages.dev`. For local development Google's guide specifies both `http://localhost` and `http://localhost:5173`. This app uses a JavaScript callback, so no OAuth redirect receiver URI or client secret is needed.
3. Copy the public client ID ending in `.apps.googleusercontent.com`. Set `GOOGLE_CLIENT_ID="YOUR_PUBLIC_CLIENT_ID"` in git-ignored `worker/.dev.vars` locally, or Worker environment variables for deployment. Leave it unset until ready; the UI honestly disables sign-in. Never add a Google client secret or ID token to source files or frontend env variables.
4. Keep `VITE_API_BASE_URL=/api`. The development Vite proxy is already configured. For localhost testing change the Worker `ALLOWED_ORIGIN` to `http://localhost:5173`, restart `npm run dev`, and open that exact URL. For deployment bind Pages `API` to `travelapp-api`, apply all remote D1 migrations through `0010_review_photos.sql`, and set the Worker `ALLOWED_ORIGIN` to the exact Pages HTTPS origin. The same-origin [Pages service binding](https://developers.cloudflare.com/pages/functions/bindings/#service-bindings) preserves cookies without relying on third-party cookies or a purchased custom domain. Workers, Pages Functions and D1 have [Free plans with quotas](https://developers.cloudflare.com/workers/platform/pricing/); no paid resources were provisioned here.
5. Open Account & favorites → Prepare Google sign-in → Google's button. Preparation explicitly loads Google's official SDK; no One Tap/automatic login is used. Then save a place, refresh the page to reopen the collection, and sign out to check revocation. Cookies always remain Secure/HttpOnly: if a browser rejects them on local HTTP, use the HTTPS Pages preview; do not weaken cookie security. Both the SDK and nonce can expire/fail; the UI offers preparation/retry and reports errors. Live Google sign-in is unverified until the client ID/origin configuration is supplied. Public launch also requires correct privacy-policy/terms URLs in Google Branding and Google's applicable consent/branding review.

The Worker verifies RS256 signatures with Web Crypto against Google's official JWK keys, plus issuer, configured audience, authorized party if present, expiry, issue time, subject and a single-use five-minute nonce. [Google's verification guide](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token) describes the signature and claim checks and recommends standard libraries; this implementation uses native cryptography to avoid adding a dependency. Tests sign real RSA tokens and check tampering, wrong claims, nonce replay and key rotation/cache expiry. Successful key responses honor Cache-Control up to 24 hours; key refreshes are gated to one per minute with timeouts. Login preparation/exchange share a ten-attempts-per-network-per-minute cap. Shared networks share this cap.

Migration `0005_accounts.sql` adds users, favorites, login_challenges and sessions. Users store Google's stable subject and a display name, not an email/profile photo. Google's token is verified and discarded; sessions store only SHA-256 hashes of random tokens, expire after seven days, rotate on login and are revoked on logout in that browser. Expired session/challenge rows are removed on later login/preparation, not by a paid scheduled service. User/favorite records persist until removed by the operator; a public deletion-request/contact process and privacy/legal review remain required before launch. Location permission and the current position are not added to account records; saved public place coordinates are retained as part of favorites.

Favorites are scoped only from the server session (client user IDs are ignored), validated and atomically capped. Exact Origin checks protect writes, session cookies are Secure/HttpOnly/SameSite=Strict with __Host prefixes, and account API responses are no-store and never service-worker cached. Account tokens/profile/favorites are not written to localStorage. The Pages API function fails visibly if its binding is missing; `_routes.json` invokes Functions only for `/api/*`, preserving static asset delivery. The normal root build now also compiles this function. No new dependencies, cloud accounts or paid services were added. Actual Google-user login, public deployment and device install remain pending.

### S2 — live location sharing (local)

Open **Share live location**, choose 1/4/8 hours, read/check consent and choose **Start sharing**. Allow location in the browser. No Google sign-in is needed. Share the private link through Copy, the share sheet, WhatsApp or the SMS composer. Sending messages is always a user action. A recipient gets a map, accuracy, server update time and a stale warning after 90 seconds. Stop deletes the latest position on the server; an unconfirmed stop explicitly warns and offers retry. Going Home/closing the tab pauses updates and leaves the link active until Stop/expiry. Reopening restores only link metadata from session storage; consent and Resume are required before GPS updates restart.

Only the latest position is stored. Updates/read polling run every 30 seconds while the sharing screen is visible, and a sender only uploads a position received within 60 seconds. API writes enforce a 15-second minimum plus per-device/network limits; they never extend expiry. Optional screen Wake Lock may fail or be released; it is not background tracking. See [Geolocation requirements](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation/watchPosition) and [Wake Lock limits](https://developer.mozilla.org/en-US/docs/Web/API/WakeLock). Clear cookies can prevent a sender from managing a share; expiry still applies. Precise location requires HTTPS or a browser-supported secure localhost origin. Actual Android/iPhone GPS, SMS/share-sheet and screen-lock behavior remain to be tested on devices; browser tests used explicitly synthetic Delhi coordinates, not an operator's GPS.

`0006_live_shares.sql` adds devices, latest-position live_shares and retired_share_keys. Device access uses an HMAC-signed random Secure/HttpOnly/SameSite=Strict cookie, independent of accounts. Recipient secrets are 256-bit HMAC values issued by the server from a random nonce and bound to the sender device, share identifier and server expiry. They are URL fragments, transmitted in authorization headers and stored only as hashes server-side. A known old recipient secret cannot be reissued by using it as a new creation nonce after retirement cleanup. The owning device can recover the issued link after an uncertain create without extending expiry. Recipients cannot update/stop shares. A sender's random share ID supports idempotent creation; ended IDs/token hashes are retained without positions for up to 30 days to block delayed creations reviving a stopped link. Creation allows one active share per device, six new shares/device/day, thirty/network/day; preparation allows ten new devices/network/hour. Shared networks share these limits. Reads allow sixty/network/minute, updates four/device/minute and 120/network/minute. API data is no-store; no service-worker route caches location responses. Tile providers can see the viewed map area; consent/privacy explain this.

A random `DEVICE_SECRET` was generated only in git-ignored `worker/.dev.vars` for local testing. For deployment generate a separate 32-byte random secret and use `wrangler secret put DEVICE_SECRET --config worker/wrangler.jsonc`; never put it in VITE variables or source. Keep the same-origin Pages API binding and exact `ALLOWED_ORIGIN`. Apply remote D1 migrations before deploying. The five-minute [Cloudflare Cron Trigger](https://developers.cloudflare.com/workers/configuration/cron-triggers/) calls cleanup even without viewers: expiry denies access immediately; stored positions are deleted on the next sharing API request or scheduled sweep. Local dev cleanup remains request-triggered. Production cleanup is deployed separately as `spotland-expiry-cleanup`, using `worker/wrangler.cleanup.jsonc`, the dedicated remote `travelapp` D1 database and `spotland-review-photos` R2 binding. All ten remote migrations are applied. It has no public HTTP endpoint, sends no alerts and needs no local credentials. Each sweep attempts location, SOS and stale-upload cleanup independently; a failed sweep is reported as a failed invocation. [Workers Free quotas](https://developers.cloudflare.com/workers/platform/limits/) and [D1 Free quotas](https://developers.cloudflare.com/d1/platform/limits/) still apply; no paid plan was enabled.

Redeploy cleanup with `npx wrangler deploy --config worker/wrangler.cleanup.jsonc`; inspect live runs with `npx wrangler tail spotland-expiry-cleanup --config worker/wrangler.cleanup.jsonc`. Before deploying the public API, bind it to the same production D1 database ID recorded in the cleanup configuration. The local API configuration intentionally retains its placeholder/local database; this cleanup deployment does not move local data or launch the frontend. Do not run the public API and cleanup against different remote databases.

Production verification on 1 October 2026: automatic cron invocation completed at 06:15:38 UTC with outcome `ok`, no exceptions and 5 ms CPU time.
